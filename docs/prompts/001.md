# IMPLEMENTATION PROMPT — DevCommander

## Context & Goal

Build **DevCommander** from scratch in this repository (`d:\dev\code\ataghav\DevCommander`, currently containing only `docs/srs.md` and `README.md`). DevCommander is a single-user autonomous-coding control plane per `docs/srs.md` (read it first — it is the requirements authority): a commander talks to a supervisor agent over Telegram; the supervisor manages missions defined in locked markdown files; each mission runs a squad — a git worktree in which a headless coding CLI (claude / codex / cursor-agent / opencode) implements tasks, a one-shot Critic agent reviews the diff, and a Verifier runs the repo's verification commands as machine truth — with bounded retries, durable SQLite state, crash recovery, budget caps, approval gates, and a notification outbox. Build the **complete end state in one pass**: no phasing, no stubs.

The stack is .NET 10 + **NovaCore.Agents 3.1.7** (NuGet). Two reference codebases are readable on this machine and are the binding standard:

- **Framework:** `D:\dev\code\work\NovaCore\NovaCore.Agents` — authoritative docs in `doc\` (`getting-started.md`, `host-integration.md`, `sessions-and-persistence.md`, `capabilities.md`, `structured-output.md`, `budget.md`, `testing.md`).
- **Host blueprint:** `D:\dev\code\akeyanjam\JobAssistant\src\JobAssistant` — DevCommander mirrors its architecture: single host project with folder layering, Telegram polling → dispatcher → keyed agent factories, an in-memory runtime registry driving background work, startup reconciliation, EF migrations applied on boot.

### Confirmed decisions (do not re-derive)

- Single host project `src/DevCommander/` + one test project `tests/DevCommander.Tests/`; solution `DevCommander.sln`.
- All **four** runtime adapters implemented now (claude, codex, cursor-agent, opencode).
- LLM provider: **`NovaCore.Agents.Providers.OpenAI` only**, using the OpenAI-compatible entry point; base URL, API key env var, and per-role model names come from configuration (`Agents` options section). Roles: `commander`, `planner`, `critic`.
- Single commander: Telegram allowlist is **config** (`Telegram:AllowedChatIds`, array of long). No user table, no setup wizard, no multi-tenancy.
- `/missions`, `/status {id}`, `/approve {id}`, `/stop {id}`, `/continue {id}`, `/start {repoId} {missionSlug}`, `/whoami` are handled **deterministically against SQLite** in the dispatcher (no LLM turn). Only free text becomes a supervisor turn.
- Approval gates (FR-022) are a **plain DB state machine**: gated command detected → `ApprovalRequest` row + squad status `WaitingApproval` + outbox notification; `/approve` flips the row and resumes the loop; reconciliation re-arms pending gates after restart. **`SuspendsForHost` is not used anywhere in this codebase.**
- Mission decomposition: an ephemeral one-shot planner factory, `RunStructuredAsync<MissionPlan>`; tasks persisted before any coder spawns.
- Critic: ephemeral one-shot factory, `RunStructuredAsync<CriticVerdict>` over the mission diff.
- Budget: `Mission.BudgetUsd` (default 5, configurable) is a host-side ledger. Accumulate coder CLI cost parsed from CLI JSON where reported (claude, codex, opencode; cursor reports none) plus `ExecutionReport.TotalCost` from planner/critic runs. Wall-time cap per mission from config. Either breach → mission `Halted`, partial work preserved.
- Squad-event notifications are deterministic text written straight to the outbox — never generated via a supervisor LLM turn. The supervisor answers status questions from DB via capabilities (FR-020).
- Secrets (LLM keys, CLI credentials, git push credentials) come from container env only; never stored in DB or git.
- Cross-platform: builds and tests run on Windows (dev machine); runtime target is a Linux container. All process, git, and clock interactions sit behind interfaces so tests never touch real CLIs, git, or the network.

### Key mechanics the codebase alone won't tell you

**Runtime adapter contract** (SRS §9):

```csharp
public interface IRuntimeAdapter
{
    RuntimeKind Kind { get; }
    Task<RuntimeResult> StartAsync(string prompt, string worktreePath, CancellationToken ct);
    Task<RuntimeResult> ResumeAsync(string sessionId, string prompt, string worktreePath, CancellationToken ct);
}
public sealed record RuntimeResult(string? SessionId, string FinalMessage, int ExitCode, decimal? CostUsd);
```

All adapters run via `IProcessRunner` with cwd = worktree, capture stdout/stderr, surface the child PID (persisted to `Squad.LastPid`). Invocation shapes (parse defensively; ignore unknown JSON fields):

- **claude:** start `claude -p --output-format json "<prompt>"`; single JSON object → `result`, `session_id`, `total_cost_usd`. Resume: `claude -p --resume <sessionId> --output-format json "<prompt>"`.
- **codex:** `codex exec --json "<prompt>"`; JSONL events → session id from the session-config event, final agent message, token usage if present. Resume: `codex exec resume <sessionId> --json "<prompt>"`.
- **cursor:** `cursor-agent -p --output-format json --force --trust --workspace <worktree> "<prompt>"`; single JSON object → `result`, session id. Resume adds `--resume <chatId>`. **Cursor sessions are scoped to the workspace path they started in** — resume is only valid when the worktree path is unchanged; otherwise fresh-spawn. No cost reported (`CostUsd = null`).
- **opencode:** `opencode run --format json "<prompt>"`; JSONL events → `sessionID` (`ses_…`), text parts, cost summed from `step_finish` `part.cost`. Resume: `opencode run --session <sessionId> --format json "<prompt>"`.

**Squad loop** (one squad per mission, driven by the registry on a background task):

1. Ensure repo clone exists under `{DataRoot}/repos/{repoId}` (clone if missing), fetch; create branch `mission/{repoId}/{missionSlug}`; `git worktree add {DataRoot}/worktrees/{missionId}` on that branch. Assert the branch is never `main`/`master` before any push (BR-007).
2. Process pending `TaskItem`s grouped by `Phase` ascending; phases sequential, each coder prompt composed from: repo `AGENTS.md` (if present) + mission file + this phase's pending tasks + previous phase's summary (coder's final message) + on retry, critic findings and verifier output.
3. Coder attempt: `Resume` when `Squad.SessionId` exists and the worktree is unchanged, else `Start`. Record cost into `Mission.CostUsd`, write `SquadEvent`.
4. Empty diff after a coder attempt counts as a failed attempt. Otherwise Critic (`RunStructuredAsync<CriticVerdict>` with `{ bool Approved, string[] BlockingFindings, string Notes }`) over the full diff since branch point (committed + uncommitted). Not approved → retry.
5. Before each verification command, check it against `Repo.GatedOps` (substring match): on match, write `ApprovalRequest(Pending)`, set squad `WaitingApproval`, enqueue notification, and park until approved (in-process wait + DB poll fallback so it also works after restart).
6. Verifier: run each verification command (mission file's section overrides repo's when it lists concrete commands; "repo default" or empty means use `Repo.VerifyCommands`) via shell (`/bin/sh -c` on Linux, `cmd /c` on Windows), cwd = worktree; capture stdout/stderr as evidence; any non-zero exit = fail regardless of what the coder claimed (BR-005) → retry.
7. Attempt cap 3 per phase (BR-003, reset per phase); normalize the failure signature (critic finding + verifier output tail) and escalate to `Blocked` + notification when the same signature repeats. Before every attempt check budget and wall-time (BR-004) → `Halted` + notification, partial work preserved.
8. Phase pass: commit uncommitted changes, mark phase tasks `Done` with evidence. All phases done: push the mission branch, mission `Completed`, completion notification.

Network-type failures (adapter/Telegram/git push) → squad `StalledNetwork`, exponential backoff retry indefinitely (NFR-09); notifications always queue in the outbox and flush on reconnect.

**Reconciliation** (FR-031): on boot, for missions in non-terminal states: dead PID (process gone) + squad was `Running` → resume via the continue path (native session resume when session id + intact worktree, else fresh spawn from ledger + `git diff` context); `WaitingApproval`/`Blocked` → leave state, re-ping. One recovery summary notification ("resumed N squads, lost M tasks") within 60 s of boot (NFR-02).

**Notifications** (FR-040): outbox rows only for mission complete, blocked/approval needed, retries exhausted, budget/wall-time breach, post-recovery summary. Everything else is a `SquadEvent`. A `BackgroundService` flushes `Queued` → `Sent` with backoff on Telegram failure.

**Entities** (SRS §8): `Repo` (Id = slug string PK, CloneUrl, DefaultRuntime, VerifyCommands, GatedOps), `Mission` (Guid PK, RepoId, Slug — unique (RepoId, Slug) —, SpecPath, Status, BudgetUsd, CostUsd, Branch, CreatedAt, ClosedAt), `Squad` (Guid PK, MissionId, WorktreePath, Runtime, Status, LastPid, SessionId, AttemptCount, LastErrorSignature), `TaskItem` (Guid PK, MissionId, Phase, Description, Status, Evidence), `SquadEvent`, `Notification` (Severity, Body, State, At, SentAt), `ApprovalRequest` (MissionId, Operation, State, CreatedAt, DecidedAt), `AppSetting` (Key, Value). Mission files live at `{DataRoot}/missions/{repoId}/{missionSlug}.md`; BR-001 validation = markdown headings for the six sections (Goal, In-scope, Out-of-scope, Verification commands, Acceptance criteria, Runtime preference); the refusal message names each missing section.

**Supervisor:** keyed factory `"commander"`, `.Store()` (EF), `Loop = Chat, MaxToolRounds = 25`, `Summarize { EveryNTurns = 10, KeepRecentTurns = 10 }` (NFR-04). Capabilities (all thin wrappers over the same services the deterministic commands use; no file/code editing tools exist — BR-008): `RegisterRepo`, `StartMission`, `MissionStatus`, `ListMissions`, `StopSquad`, `ContinueMission`.
